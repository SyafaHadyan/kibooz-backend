# Design notes

How accounts, sessions, rate limits, Redis and the business rules behave. The routes, fields and error codes are in the API reference at <https://docs.kibooz.syafahadyan.com>.

## Accounts

There is no seed data. Accounts come from `POST /auth/register`.

- A GURU registers together with a new class (`class.name` is required) and becomes its teacher. The class gets an eight character `joinCode` that the dashboard returns. A class that was created when codes had six characters got a new eight character code from migration 000010 when the API first started with it, and the old code stopped working.
- A WALI registers with the teacher's `classCode` and the child's `student.nisn` and `student.fullName`.
- A GURU cannot join an existing class with its code, so knowing a class code never gives access to its children's data. A teacher of the class can add another registered teacher by email with `POST /guru/classes/{classId}/teachers`, and that is the only way a class gets more than one teacher. Each class has one owner in `class_teachers.is_owner`, enforced by a partial unique index. The owner removes teachers with `DELETE /guru/classes/{classId}/teachers/{teacherId}` and hands the class on with `PUT /guru/classes/{classId}/owner`, and any teacher can remove themselves. The only active teacher cannot leave, so a class keeps a teacher and an owner. When the owner leaves, or deletes the account, the teacher who joined next becomes the owner. A teacher who is the only teacher of a class cannot delete the account without naming a successor in `successorEmail`, so a class is never left without a teacher. Every change of the teachers of a class takes one advisory lock for that class, so two teachers that leave together cannot both be the one who is not last.
- ADMIN exists in the role enum but cannot be registered.

## Rate limits

No rate limit looks at the IP address. A school network or an ISP puts many people behind one public address, so an address says little about who is asking and one noisy person would throttle everyone else on it. The `TRUST_PROXY` setting only decides which address the access log shows. Every limit is a sliding window of `LIMITER_EXPIRATION_SECONDS` and answers `429` with `RATE_LIMITED` and a `Retry-After` header. A request that is refused still counts, so `Retry-After` is the time until a request fits again with the refused ones included, and a client that keeps sending gets a longer wait, up to the rest of the window and the whole next one. `X-RateLimit-Reset` has the same value on a refused request and the seconds until the window ends on any other. The daily limit of trash claims is not one of these limits, it answers `429` with `TRASH_DAILY_LIMIT_REACHED` and no `Retry-After` header.

| Where | Counted per | Allowance |
|:---|:---|:---|
| Every route that needs a signed-in user | user id | `USER_LIMITER_MAX`, 120 by default |
| Deleting an account, which confirms the password | user id | `AUTH_LIMITER_MAX`, 10 by default |
| Login and register | email, or the device when the login carries a valid device token | `AUTH_LIMITER_MAX`, 10 by default, separately for each route |
| Refresh token and logout | refresh token | `AUTH_LIMITER_MAX`, 10 by default, separately for each route |
| Register with a class code | the whole API | `CLASS_CODE_LIMITER_MAX`, 60 by default, on top of the limit per email |
| `/healthz` | nothing | not limited |

Each route is limited by the one field it actually reads, so adding a second field to the body, such as an email on a refresh request, does not give a caller a new budget. The email is trimmed and lower-cased the same way the sign in does it, so changing the letter case does not either. The identifiers are hashed before they become a storage key, so no email or token is kept in Redis in clear. A request that names no account, such as an empty or malformed body, is not counted, because it is rejected before it touches the database.

The counters live in Redis when it is reachable, so every instance of the API shares them. This needs one Redis, which can be a single server or a primary with replicas. Redis Cluster is not supported, because the client does not speak its protocol, and a proxy that spreads keys over several servers would break the transaction below, which touches the counters of two windows. A request is counted with atomic commands in one transaction, `INCR` on the counter of the current window and a read of the previous one, and no instance reads a count to write it back, so instances that count at the same moment never lose a request. Windows are the consecutive stretches of `LIMITER_EXPIRATION_SECONDS` since the Unix epoch, so the instances agree on where a window starts as long as their clocks are in sync. The sliding window counts the previous window for the part of it that the last window still covers, rounded up. Only the count of each window is kept and not the time of each request, so this is an estimate that assumes the requests of the previous window were spread evenly, and rounding up only keeps truncation from losing a whole request at the start of a window. No lock is held while the API waits for Redis, so a Redis that is far away slows each request by one round trip and does not queue the requests behind one another. Without Redis each process counts for itself. When other applications use the same Redis, set `REDIS_KEY_PREFIX` and every key of the API starts with it, and the e2e tests of this repository need a `REDIS_DATABASE` of their own because they empty it.

### Trusted devices

Anyone who knows an email can use up its shared login budget, so a limit per email alone would let a stranger keep the owner from signing in. To prevent that, registration and login return a `deviceToken` that the app keeps and sends in the next login request. A login that carries a valid token for its email is counted in a bucket of that device, and every other login is counted in the shared bucket of the email. A stranger can only fill the shared bucket, so the devices that have signed in before keep working.

The token is not a credential and never replaces the password. It is signed with a key derived from `JWT_SECRET_KEY`, bound to the email, valid for `DEVICE_TOKEN_TTL_DAYS` (90 by default) and renewed by every login, and a token refresh does not return one. A forged, expired or foreign token is rejected by the signature alone, without a database lookup, and the request falls back to the shared bucket. A stolen token only gives the thief the same `AUTH_LIMITER_MAX` attempts per window in the bucket of that one device, and the password is still needed.

A new device, or one that cleared its data, has no token and uses the shared bucket. While someone is using it up, that device cannot sign in until the window passes.

A class code is the only secret between a stranger and a class, and a wrong code is answered at once with `CLASS_CODE_NOT_FOUND`, before any password is hashed. So the number of guesses is limited for the whole API and not per caller, because a guesser can use any number of emails and devices. Once the budget of a window is used up every registration that names a code gets `429`, the right code included, so the answer reveals nothing while the budget is gone. The price is that a flood of guesses can keep parents from joining a class for as long as it lasts. Eight characters from an alphabet of 32 make about 1.1e12 codes, so even a budget that is spent in full in every window needs decades to hit a code when a thousand classes exist. Six character codes would be far easier to find, because there are only about 1e9 of them and a thousand classes would be found in about 12 days at the default budget, which is why migration 000010 replaced every one that existed.

Two things follow from not using the address. Guessing the password of one account is stopped from any number of addresses, and anyone can still send `AUTH_LIMITER_MAX` failed logins for someone else's email to block new devices for that person for a window. A flood that names a new account in every request, such as thousands of sign ups with random emails, is not stopped by the API at all, so keep a limit in front of it in the reverse proxy or the CDN.

### A flood limit in the proxy

The proxy limit is a ceiling for floods and not a throttle for people. It counts by address, so once an address goes over the limit the proxy rejects everyone who shares it, including the users who behave. Only login and register hash a password, so those two routes get a strict limit and every other route is left to the API. This nginx example allows each address 5 requests a second with a burst of 30. Several teachers who sign in at the same moment on one school network stay inside the burst, and a single script is held to a few requests a second.

```nginx
# http block
limit_req_zone $binary_remote_addr zone=kibooz_hash:10m rate=5r/s;
limit_req_status 429;

# server block
location ~* ^/api/v1/auth/(register|login)/?$ {
    limit_req zone=kibooz_hash burst=30 nodelay;
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

- **The match ignores case and allows a trailing slash**, because the router does the same. An exact match would let `/API/v1/auth/Login` or `/api/v1/auth/login/` reach the API without the limit.
- **Keep the plain `location /`.** Without it every other route answers `404`.
- **Both locations set `X-Forwarded-For` from `$remote_addr`.** `$proxy_add_x_forwarded_for` would append to the value that the client or the CDN sent, so a client could put its own addresses at the front of the header.
- **A request that nginx limits gets a plain `429`** without the `RATE_LIMITED` body, so the apps treat any `429` as a signal to wait.

If a CDN or load balancer sits in front of nginx, restore the visitor address first. With Cloudflare, set `real_ip_header CF-Connecting-IP;` and add one `set_real_ip_from` line for each range that Cloudflare publishes at `cloudflare.com/ips`. nginx only trusts the header on a connection from a listed range, so a client that reaches the server directly cannot forge it. Without this step every request arrives from the address of the CDN, all visitors share one budget and the limit blocks everyone at once. The ranges change rarely, so compare them with the published list now and then. A request that reaches the server directly skips the CDN and its rules, so allow port 443 only from the CDN if you can. A CDN rule on the same two routes works the same way and stops the flood before it reaches your server.

## Redis is optional

PostgreSQL is the only authority for sessions. Refresh tokens live in the `refresh_tokens` table as SHA-256 hashes, and a token is used by a single atomic `UPDATE ... RETURNING` that sets `used_at`, so it can be used exactly once even under concurrent requests. Every sign in has a `family_id` that its tokens share, and the used rows stay for a week. A used token that is shown again more than a minute after its use, which is the time Redis flags it for, is taken for a theft. The whole family is deleted, the owner is logged and both the thief and the owner have to sign in again. Within that minute the token is only refused, because a client that lost the answer retries with the same token. `session_started_at` is copied to every token of the family and caps the expiry of the next token at `JWT_SESSION_MAX_DAYS`, 90 by default, so refreshing cannot keep a session alive for ever. Signing out deletes the whole family.

Redis never decides that a token is valid. It only remembers consumed tokens for a minute so a quick replay is rejected without a database call, and it holds the leaderboard cache and the shared rate limit counters. This also means a stale or restored Redis cannot revive a revoked token.

When Redis is unreachable the API logs it once and keeps serving. Calls to Redis are skipped for 5 seconds after a failure, and then one call tests whether Redis is back while every other call goes on without it. So an outage costs one slow call (up to about two seconds) every five seconds and not one for each request. Only an error that says Redis cannot be reached or cannot serve opens this pause. A caller that gave up on its own request does not, and neither does an answer that refuses one command, such as a wrong key type or a missing permission, which is logged at most once a minute. Rate limiting falls back to per-process counters, the leaderboard is read from PostgreSQL, and `/healthz` reports `degraded`. When Redis returns, it is picked up again automatically.

## Idempotency keys

A client that queues an action while it is offline sends the same `Idempotency-Key` with every try. The middleware in `internal/idempotency` runs after authentication on the ten routes that create something, and a request without the header passes through untouched.

The keys live in the PostgreSQL table `idempotency_keys` and not in Redis, because Redis is optional here and an outage would turn every repeat into a duplicate. A row is claimed with one `INSERT ... ON CONFLICT` before the work starts, so two tries at the same time cannot both run. The row holds a SHA-256 fingerprint of the method, the address and the body, the status code and the response. A repeat with another fingerprint is refused, and a repeat of a finished request gets the stored response.

- Only a `2xx` response is stored. Any other outcome deletes the claim, so the client can send the same key again.
- A claim without a response that is older than the request timeout plus 30 seconds counts as abandoned and the next try takes it over, so a process that crashed in the middle does not block the key.
- Every claim has its own id and a request stores its response or frees the key only while its claim is still the one on the row. A try that was taken for dead and finishes late therefore cannot free or fill the claim of the try that took the key over.
- A row older than `IDEMPOTENCY_TTL_HOURS` (168 by default) is taken over as well and an hourly sweep deletes it.
- The claim is made before the work and the response is stored after it, in two statements. If the process dies between the commit of the work and the write of the response, a try after the abandon time repeats the work. This is rare and it is the usual trade of the middleware approach. Writing the claim in the transaction of each route would close it and needs changes in every repository.
- A response over 1 MiB is not stored and its claim is deleted. No route produces one today.

## Business rules

- A student can claim at most `TRASH_DAILY_LIMIT` times per local day. The check, the point update and the re-ranking run in one transaction guarded by a per class advisory lock, so parallel requests cannot exceed the limit.
- A new semester starts the leaderboard over. Every child has `current_points` for all semesters and `season_points` for the semester under way, and the ranking, the leaderboard and `classRank` follow `season_points`. The API checks the calendar when it starts and then every minute, so the points earned between the start of a semester and the check, a minute at most unless a check fails or the API is down, still count in the semester that ended. When the semester of the current date (named by its first day, such as `2026-07`) is not the latest one in `leaderboard_seasons`, one instance inserts it, copies the standings to `leaderboard_history` under the label of the semester that ended, sets every `season_points` to zero and clears the cached leaderboards. The insert is the guard, so instances that notice at the same moment reset once. The first run on a database only records the semester under way. The classes are locked in a fixed order like a claim locks its class, so a claim lands wholly before or after the reset. `GET /leaderboard/history` reads the saved standings, a page of semesters at a time with the newest first, and it leaves out the children whose account was deleted so no name is shown after its account is gone, while a semester stays listed even when none of its children are left.
- Ranking is points descending, then name, then id. `students.rank_position` is kept in sync on every claim and registration.
- Only the latest mood of a student per local day counts in dashboards and charts.
- A mood log may carry `recordedAt`, the time the device saw the mood, so a log that was queued offline and replayed later is dated when it happened and does not take the place of a newer mood. The time is checked against the server clock. A time more than 5 minutes ahead of it is refused, one that is less than 5 minutes ahead counts as now, and one older than 7 days is refused, which is the retention of the idempotency keys. Without it the log is dated when the server receives it. A batch has one `recordedAt` for all its entries.
- A teacher who is the only teacher of a class that still has an active child has to name another registered teacher as `successorEmail` to delete the account. The successor is added to every class that nobody else teaches and becomes its owner, and the classes that other teachers also teach go on with them as described above. Without a successor the deletion fails with `SUCCESSOR_REQUIRED` when such a class exists, and a class that nobody else teaches and that has no active child is archived instead (`classes.archived_at`), where children in the trash do not count as active. Archiving keeps the rows and the join code, so the code is never given to another class, and an archived class answers `CLASS_CODE_NOT_FOUND` to a registration or to `POST /wali/children`. The count of the children and the archive run under the class lock, and a registration takes the same lock and looks at `archived_at` again after it, so a child cannot join a class that is being archived. A named `successorEmail` is still used for every class, empty ones too, and no route restores or purges an archived class. With an email that is no active teacher account the deletion fails with `TEACHER_NOT_FOUND`. The whole deletion is one transaction, so a refusal changes nothing. The accounts of the teacher and the successor are locked in the order of their ids and then the classes in the order of their ids, so a successor that deletes its own account at the same moment is either seen as deleted and refused, or hands over its classes first. A class with children therefore never has a deleted teacher as its last one, and `CLASS_NO_ACTIVE_TEACHER` stays only as a guard for data that was written before this rule.
- Deleting an account is a soft delete. The user, their profile and a parent's children get a `deleted_at` time and disappear from every query, login and refresh token, and the class ranking is renumbered. Moods, scans and guidance records stay in the database. The avatar of the user, the avatars of the children and the photos of their trash scans are deleted from the bucket and their addresses are cleared, so no photo of a deleted account is kept. The keys of those files are written to the `file_cleanups` table in the same transaction that deletes the account, so a crash cannot make the API forget them. The API then deletes the files and takes their keys off the table, and a file that cannot be deleted at that moment is logged and stays there. The API tries what is left every ten minutes (100 files per sweep, the ones with the fewest failed attempts first) until the bucket removes it. The response of the deletion does not depend on that, because the account is gone either way. Email, NIP and NISN are only unique among active rows, so they can be registered again, and permanent removal is not automated.
- A teacher can only record and read moods of classes they teach. A parent can only read their own children. Cross class access returns 403 or 404.
- Photos are size checked and type checked by their content, not by file name, and they are stored without their metadata. The EXIF, XMP, IPTC and comment details, such as the location the phone wrote into the photo, are cut out of the file without decoding or re-encoding it, so the pixels stay exactly as they were. The orientation of a JPEG or WebP photo is kept, so a photo does not show up sideways. What stays is a list of the parts that a format needs, and every other part is dropped, including the content credentials of C2PA and chunks that no one has invented yet. A JPEG keeps its JFIF header without the thumbnail, its ICC color profile and the fields of its Adobe color segment. A PNG keeps its critical chunks and the chunks for transparency, color, physical size, background and animation, and a PNG with a critical chunk that is not on the list is refused, because a reader needs it to interpret the image. A WebP file keeps its image data, alpha channel, animation frames and color profile, with the unknown chunks inside the frames dropped too. A color profile decides how the colors look and describes a device and not a person, although the text of a profile, such as its description and copyright, stays with it. A file whose structure does not parse is refused as an invalid image. An image of more than 40 megapixels or with a side longer than 8192 pixels is refused with `IMAGE_DIMENSIONS_TOO_LARGE`, judged by its header and without decoding it, because a file of a few MiB can announce billions of pixels and every app that shows it has to allocate memory for all of them. The server never decodes or resizes a photo, so it does not need that memory, and it leaves the scaling to the apps. Raw face photos are never accepted because mood detection runs on the device.
