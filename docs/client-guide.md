# Client guide

This page is for the people who build an app against the API. The full contract is the [API reference](https://docs.kibooz.syafahadyan.com), and this page only explains the parts that an app has to do on its own.

## Base URL

The API is served over HTTPS at `https://kibooz-api.syafahadyan.com`. Every route lives under `/api/v1`, for example `https://kibooz-api.syafahadyan.com/api/v1/auth/login`, and only the health probe `GET /healthz` lives at the root. Plain HTTP requests are redirected to HTTPS, so always configure the app with the `https://` address.

## Sign in and keep the tokens

Registration and login return an access token and a refresh token. Use the access token on every request and keep both tokens in secure storage, which is the Keychain on iOS and the Keystore on Android.

A refresh token works once. Every successful call to `POST /api/v1/auth/refresh-token` returns a new refresh token, so replace the stored one each time and never reuse the old one. A call that fails returns an error and no token, and the error `AUTH_REFRESH_INVALID` means the session is over and the person has to sign in again. A session also ends by itself `JWT_SESSION_MAX_DAYS` days after the sign in, 90 by default, however often the token is refreshed. If an old refresh token is sent again more than a minute after it was used, the server takes it for a stolen token and ends the whole session, including the newest token, so the person has to sign in again. A client that does not save the new token before it sends the next request can cause this, so write the new token to storage first. Signing out ends the whole session. Send a refresh request when the access token expires and not on every launch. `PUT /api/v1/users/me/password` changes the password of the signed in account from the current password and a new one of 8 to 72 bytes that differs from it. A wrong current password is `403 AUTH_PASSWORD_INCORRECT`, and a success ends every session of the account, so the app has to send the person to the sign in screen on every device. An access token that was already issued keeps working until it expires. A forgotten password cannot be reset yet, because the API sends no email.

## Keep the device token

Registration and login also return a `deviceToken`. It is not a credential and the app never needs it to sign in. It only gives this device its own login budget for that email, so someone who types wrong passwords for the same email cannot keep the owner from signing in.

- Store it next to the account, one token for each email, because a token only works for the email it was issued for.
- Send it as `deviceToken` in the next login request for that email.
- Replace the stored token with the one in every login response, because each login renews it for another 90 days by default.
- Keep it after logout. A token that was kept lets the device sign in again even while a stranger is using up the shared budget of the email.
- Do not worry about a stale one. A token that expired or does not match the email is ignored and the login is counted in the shared bucket. If that bucket is used up, the login returns `429` with `RATE_LIMITED`, the same as for a device that has no token.

A token refresh does not return a device token, so leave the stored one as it is.

## Class videos and forum

The learning videos and the forum of a class live under `/api/v1/classes/{classId}`. The teachers of the class and the parents of a child in it can read and write there, and anyone else gets `403` with `AUTH_FORBIDDEN`. That includes a class that does not exist and a class that a teacher no longer teaches, so a teacher who was removed from a class sees `403` here and `404` with `CLASS_NOT_FOUND` on the `/api/v1/guru/classes/{classId}` routes. Treat both as a class that is gone and return to the class list. A teacher finds the class id in `classOverview.classId` of the dashboard and a parent finds it in `student.classId` of the dashboard.

A teacher can create more classes with `POST /api/v1/guru/classes`, and every class has its own join code for parents. A teacher who is the only teacher of a class that still has children must send the email of another registered teacher as `successorEmail` in `DELETE /api/v1/users/me`, who takes the class over as its owner, and the deletion fails with `409 SUCCESSOR_REQUIRED` without it or `404 TEACHER_NOT_FOUND` when no teacher has that email, so ask for the email before the final confirmation. A class that nobody else teaches and that has no active child needs no successor, and it is archived when the teacher deletes the account without a `successorEmail`. With a `successorEmail` the successor takes that class over like any other and it stays active. An archived class answers `404 CLASS_CODE_NOT_FOUND` to its join code and the API has no way to restore it, so tell the teacher that before they confirm a deletion without a successor. A teacher closes a class for new children with `PUT /api/v1/guru/classes/{classId}/joining` and the body `{"joinOpen": false}`, and opens it again with `true`. Any teacher of the class may do it, the join code stays the same, and every class starts open. While it is closed a parent who enters the code gets `409` with `CLASS_JOINING_CLOSED`, at registration and when adding a child, and children who are already in the class are not affected. `joinOpen` is part of the class in `GET /api/v1/guru/classes`, `GET /api/v1/guru/classes/{classId}` and `classOverview` of the dashboard, so show it next to the join code. A teacher replaces the code of a class with `POST /api/v1/guru/classes/{classId}/join-code`, which returns the new `joinCode`. The code is also replaced when a teacher is removed from the class or leaves it, because that teacher knows the old one, and the teachers who stay read the new code from `GET /api/v1/guru/classes/{classId}`. Deleting the account of a teacher does not replace it. The old code stops working at once and parents who already joined are not affected, so show the new code to the teacher and tell them to share it again. The teachers of a class come from `GET /api/v1/guru/classes/{classId}/teachers`. The `id` of an entry is the id that the routes to remove a teacher and to hand over the class take, and it is not the id of the account. Use `isSelf`, or compare `userId` with the id of the signed in user, to find the entry of the signed in teacher, for example to offer "leave class" on that row only. The register of a class at `GET /api/v1/classes/{classId}/students` is for teachers only. Only a teacher can add a video. A video is an https address that the player streams, either a link to another host or a file the teacher recorded. To upload a file, call `POST /api/v1/classes/{classId}/videos/upload-url` with the `contentType` (`video/mp4` or `video/webm`) and the exact `sizeBytes`, then send the file with a `PUT` to the `uploadUrl` of the answer with the `Content-Type` header it lists and nothing else, before `expiresAt`. Then add the video with `POST /api/v1/classes/{classId}/videos` and the `videoUrl` of the answer. Adding fails with `400` while the file has not arrived, so retry after the upload finishes. The upload address only holds the file for a while, so adding moves it to a permanent address and the added video returns that one as its `videoUrl`. Play the video from the address it returns and not from the one of the upload. A file that was just uploaded can be added once, and one that is never added is removed from the bucket after a day. The permanent address that the added video returns can be used again for another video of the same class, for as long as a video still uses the file. A file larger or of another type than announced is refused by the bucket. A teacher changes the title, description, thumbnail or duration of a video with `PATCH /api/v1/classes/{classId}/videos/{videoId}` and deletes it with `DELETE` on the same path. In a `PATCH`, a missing field stays, an empty `description` or `thumbnailUrl` clears it, and a `durationSeconds` of 0 clears the duration. An unknown video of that class returns `404` with `VIDEO_NOT_FOUND`. A thread has a title and a body, a reply has a body, and a reply cannot be answered again. The `author.id` of a post is the id of the account, so compare it with the id of the signed in user to mark your own posts. Posts of a deleted account stay and show `Deleted account` as the name. The author of a thread changes it with `PATCH /api/v1/classes/{classId}/forum/{postId}`, which takes a `title`, a `body` or both, and the author of a reply changes it with `PATCH` on `/forum/{postId}/replies/{replyId}`. Nobody else can change the words of a post, not even a teacher. The author can delete a post with `DELETE` on the same paths and so can a teacher of the class, and deleting a thread deletes its replies. Both are answered with `403` for anyone who may not, and with `404` and `FORUM_POST_NOT_FOUND` when the thread or reply is not at that path. Every thread and reply has an `editedAt` that is `null` until the author changes the words, so show an "edited" label when it is not `null`. A `PATCH` that leaves the words as they were does not set it.

Every list returns one page at a time. Send `page` (from 1) and `limit` (from 1 to 50, 20 by default) in the query string, and use `total` in the response to know when the last page is reached. A page past the end returns an empty list. Videos and threads come newest first and replies come oldest first.

## Send photos

The server never decodes, resizes or compresses a photo. It checks the type and the size, cuts out the metadata and stores the picture with its pixels unchanged, so the app has to make the photo small before it uploads it. Scale the longest side down to about 1600 pixels and save it as a JPEG with a quality of about 80, which is enough for a screen and usually far under the limit of 2 MiB for an avatar and 4 MiB for a trash photo. Check the size of the encoded file against the limit that applies, and lower the dimensions or the quality when it is over, because a file over the limit is refused with `FILE_TOO_LARGE`. An image of more than 40 megapixels or with a side longer than 8192 pixels is refused with `IMAGE_DIMENSIONS_TOO_LARGE`, even when the file is small, and a file that is not an image is refused with `INVALID_IMAGE`. Show the person a short message for each of these and let them pick another photo.

## Show smaller photos

An avatar is stored at the size the app uploaded, so a list of many people should not download every original. The media host can resize a photo on request. Put `/cdn-cgi/image/` and a list of options in front of the path of the address that the API returned. For an `avatarUrl` of `https://kibooz-media.syafahadyan.com/avatars/<id>/<file>.jpg` the address of a 128-pixel-wide copy is `https://kibooz-media.syafahadyan.com/cdn-cgi/image/width=128,quality=80,format=webp,onerror=redirect/avatars/<id>/<file>.jpg`. The result keeps the proportions, so ask only for a width.

Use the same options every time and pick the width from a short list, such as 128 and 256 for avatars, because every combination of photo and options is counted once a month and the free allowance is limited. Do not add other options or a query string, and do not build a width from the screen size of each phone. `onerror=redirect` sends the app to the original photo when a copy cannot be made, which is what happens after the allowance of a month is used up, so always keep it and let the image view load whatever comes back.

This only works for addresses on the media host. A thumbnail that is a link to another site stays as it is. A photo that a person replaces gets a new address, so the copies of the old one never go stale.

## Repeat a request safely

An app that queues an action while the phone is offline can send it again without the risk of doing it twice. Make one random key for the action, a UUID is a good one, and send it in the `Idempotency-Key` header with every try of that action. A new action gets a new key.

The header is accepted by the routes that create something, which are `POST /trash/scan-claim`, `POST /guru/mood/log`, `POST /guru/mood/log/batch`, `POST /wali/guidance/apply`, `POST /wali/children`, `POST /guru/classes`, `POST /guru/classes/{classId}/teachers`, `POST /classes/{classId}/videos`, `POST /classes/{classId}/forum` and `POST /classes/{classId}/forum/{postId}/replies`. The other routes ignore it.

- A try after one that worked gets the first answer again, with the same status and body and the header `Idempotent-Replayed: true`. Nothing is written a second time, so a claim does not use the daily limit again and a mood is not logged twice.
- Only a `2xx` answer is remembered. After a `400`, a `403`, a `429` or a `5xx` the same key can be sent again, for example after the person fixed the input or the rate limit ended.
- The same key with a different request is refused with `422` and `IDEMPOTENCY_KEY_REUSED`. A repeat has to be the same method, address and body as the first try.
- The same key while the first try is still running is refused with `409` and `IDEMPOTENCY_IN_PROGRESS`. Wait a moment and send it again.
- A key has 8 to 64 letters, digits, dashes or underscores, otherwise the answer is `400`. It belongs to the signed in user, so two users can never meet each other's keys.
- The server remembers a key for 7 days by default, so a phone that stays offline over a long weekend can still repeat its queue.

A request without the header works as before. The header only protects an action that the app sends more than once, so keep the key with the queued action until the app has seen a `2xx` answer for it.

## Send plain request bodies

Send JSON bodies as they are, with no compression. A request with a non-empty `Content-Encoding` header other than `identity`, such as `gzip` or `zstd`, is refused with `415` and the code `BAD_REQUEST`. Most HTTP clients add that header only when told to, so the usual fix is to turn request compression off.

## Handle rate limits

`POST /guru/mood/log/batch` has a limit of its own, 30 requests per minute for each user by default (the window is the `LIMITER_EXPIRATION_SECONDS` of the server, 60 seconds by default), because one request writes up to 30 logs. A class of 30 children needs one request, so an app that sends one batch per class stays under it as long as it handles no more than 30 classes in a minute.

A request over a limit gets `429` with the code `RATE_LIMITED` and a `Retry-After` header. Wait that long before the next try and show the person a short message. Sign in, sign up, changing the password and deleting the account can also answer `429` with `RATE_LIMITED` and `Retry-After: 1` when the server is busy checking passwords. That one is not a limit on the person, so wait the second and send the same request once more before showing an error. An earlier try is refused and counted, so it only makes the wait longer. A reverse proxy in front of the API can also answer `429` with no body and no `Retry-After` header, so check the status code first and wait about 30 seconds when the header is missing, doubling the wait on each further `429`. `POST /api/v1/trash/scan-claim` can also answer `429` with `TRASH_DAILY_LIMIT_REACHED` once a child has used the claims of the day. That answer has no `Retry-After` header and the limit resets at midnight of the local day, so tell the person to come back tomorrow and do not retry. Always branch on `errorCode`. Do not retry in a loop, because every retry counts against the same limit. A `429` that has no JSON body comes from a proxy in front of the API and means the same thing.

A child can have at most 20 mood logs on one local day, so a teacher who records the same child again and again gets `409` with `MOOD_LOG_LIMIT_REACHED`. A batch is refused as a whole and `details` names the entries to drop. Do not retry the same entries, because they fail until the next day. The notes of a mood log and the `parentNotes` of a guidance report are at most 500 characters.

The API never limits by network address, so a whole classroom on one network does not slow each other down. Routes for a signed-in user are limited per user. Registration and login are limited per email, or per device when the login carries a valid device token, and each of the two routes has its own budget. Refresh and logout are limited per refresh token, again with a budget for each route. A proxy or CDN in front of the API can add its own limit per address, and a very busy shared network can still get a `429` from that. The numbers and the reasons are in the [design notes](design.md#rate-limits).

## When the API is down

A request that cannot connect, or that gets `502`, `503` or `504` without a JSON body, comes from the network or the proxy and not from the API. Treat it like a `429` without a `Retry-After` header above, and retry with a growing wait. A `500` with `INTERNAL_ERROR` means the server broke, so retry a creating request only with the same `Idempotency-Key`. The [status page](https://status.syafahadyan.com/) shows whether the API or the documentation site has an open incident, so an "unavailable" screen in the app can link to it.
